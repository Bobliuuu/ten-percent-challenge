## 2. Rule 4: strongest attacks and answers
Common attack (all three): feedback is MEMIT. `dW = R K^T (...)^-1` is a sum of outer products whose right factors are the annotated items' own MLP activations. The patch IS a key-value memory keyed on the annotations: an input is "looked up" by its inner product with stored keys, and the value is a shift along `W_U[Recipe]-W_U[competitor]`. This is the lm_head-row edit of the rejected entries moved one step earlier (4b: "the same head as before, just kept inside the model file"). Evidence the attacker will use: shuffled arm teaches 0.005 (L1): the edit does not generalise a bias, it fires only for inputs near annotated keys, i.e. nearest-neighbour behaviour; patch.pt is fitted fp16 data (50.3 MB) stored beside 1-bit weights; "annotations not stored" is true but their activations are, in compressed form.
Answers: (a) nothing is looked up outside the forward pass: the model's own computation, with edited weights, emits the label token end to end, no external table, no classifier, no prompt; (b) the dev/locked evidence of cross-source transfer (L1 MTOP .95 / HWU64 .80 never used for annotation) shows generalisation beyond near-duplicates; (c) empty feedback leaves the tree byte-identical; (d) the maintainer already accepted that weight edits are open (RULES 4d "not yet ruled"). Residual risk is real and unruled: classify all three feedback mechanisms GRAY-high.

### 2.1 L1
- `answer.py`/`common.py`: pure HF generate, greedy, no menu logic, label decoded as text. Clean. The task prompt lists 7 labels, `Recipe` is absent (no menu leakage). Note the base itself emits `Recipes` for ~10/300 annotation-pool items ("Recipe" is one letter from a word the model already knows), so the new label is partly in-vocabulary: weaker than a truly unknown word (L2 dev Jukebox/Briefing and L10 are better evidence).
- `feedback.py`: no lookup, but (i) `feedback_calib.jsonl` (182 unlabeled prompts, 45.5 kB) is shipped and counted and also feeds the covariances `C`, `C_ans` that decide the solve: attack "fitted computation / side memory". Answer: unlabeled, 0.03% of bytes, a regulariser; honest label: GRAY. (ii) the calibration sequences include the model's own greedy answers = self-distillation targets. (iii) `patch.pt` stores fp16 replacement columns: a fitted 50 MB table. Answer above.
- Attack (R9): Bonsai-8B is not our compression. The repack is lossless (bit-exact), so "retention 1.000" measures nothing; the compression side carries zero credit, and by the plain reading (original = Qwen3-8B fp16) retention is 88.9% => FAIL.

### 2.2 L2
- `feedback.py` shells to `fb27s.py`; edits `mlp.down_proj` of layers 62,63 (last two) by Cholesky solve with covariance from `data/exam/cal.jsonl`. That calibration file is **labelled** (rows carry `answer`; the covariance is computed on prompt + gold answer tokens) and is named `exam/cal` (it is the shared `cal_big` subset; disjoint from exam by text, verified). Attack: labelled data fitted into a computation. Answer: only second moments, same family as L1 (unlabeled variant would be cleaner). Fix: rebuild covariance from the model's own answers like L1.
- The shipped `ship/feedback.pt` is a real Recipe delta (4.5 MB) sitting in the shipped tree: the "clean" artifact already contains a feedback state unless the maintainer deletes it. Fix: ship without feedback.pt; counts as bytes only after the maintainer's own feedback.
- Annotation pool is 100% Recipe items, so "real mistakes" are all one class; the shuffled arm cannot permute labels (see rule 6).

### 2.3 L9b
- Carrier = replaced bf16 columns (512 per layer, 10 layers, 20.98 MB) of the dense shared-expert `down_proj`: same MEMIT family. Annotations mix 12 Recipe + 13 old-skill errors; the 13 "real errors" are picked from the cal pool (the same prompts used for expert-selection mass and covariances): not exam, but annotation = calibration data.
- Expert pruning by routing mass on SKILL7 prompts = task-fitted, data-dependent structure. Rival #4 does the same with 43% kept; the maintainer has not ruled yet, so GRAY, but it is the strongest rule-9 exposure here (see section 5).

## 4. R7 / R8 / R9 spirit attacks
- R7 real output: L1 exact string; L2 first-word lowercase scoring with `max_new_tokens=6`; L9b first-line normalised, 8 new tokens. For all, the "real job" is a 1-word label from a 7-way menu: the maintainer may call a closed-menu label a classifier output (the menu is in the prompt). Defence: free-text generation, new unseen word emitted.
- R8: bases are .907/.967/.968, the latter two leave ~3% headroom and per-cell ceilings (several kinds at 1.0 for base). L1's weakest dev cell is .52 (CLINC Alarm: timers), so L1 has the most "something to keep".
- R9 pre-compressed start: L1 and L2 both start from an already-1-bit/ternary release; L1 adds no compression. Mitigation already in RULES 4f; L2 is defensible (own recompression, passes vs the fp16 ancestor too, 9.62% real denominator); L1 is not. If the maintainer reads "original" as the fp16 ancestor, L1 fails rule 2 (88.9%) and L2 passes.
- Task narrowness: voice-skill routing over 7 skills (MASSIVE/CLINC/HWU64/MTOP intents) is the same shape as rival #4's task. It is a commercial task but with a tiny label set; the "10 intents x 5 examples" style routers are exactly the kind of "narrow distribution" rule 1 warns about. An entry showing a second, broader task would defuse this (no entry has one at the final gate).
- Hash slices / exam reuse across lanes: the shared exam is used by L1, L2, L9b, L10; each scored it once per model, but L9b's three artifacts and L1's three base runs were all scored on the one exam, and configs for L2 (layers 62,63, m=8) came from a NEWS dev sweep. No best-of-N on the exam. Other lanes' private exams (L9 `EXAM_SEAL.json`, hash-bucketed) are different data and not shared.
- Disk/repo: committed artifacts contain full exam texts (v2/exam/data); fine by the maintainer-check wording ("ship the locked files").

## 5. Maintainer-own-data attack (different distribution + own feedback)
Predicted failures and cheap tests (not run; see top):
1. **Different label set / task**: the answer prompt in all three entries is hardcoded to the 7 skills (L9b `answer.py` hardcodes the prompt string; L2 `answer.py` hardcodes it unless `--labels`; L1 needs `--task task.json`, ok). A maintainer task with other labels needs a prompt rewrite: L1 is the only entry with a generic `--task`. Fix: make all three accept a task JSON.
2. **Expert-pruned L9b** keeps 102/256 experts chosen on voice-skill prompts. On other text (banking, PII, different language) routing mass shifts to pruned experts; the BANK6 run of the same recipe fell to 97.37% retention with Card 94.4 (fails gate). Predict: L9b degrades hardest out of distribution. Cheap test: run base vs packed on 300 unrelated prompts (e.g. Banking77) and compare outputs.
3. **New label close to an old one** (e.g. `Timer` vs Alarm, `Reminder` vs Calendar): all closed-form edits fight old labels. Recipe is far from the menu: the easy case. Cheap test: annotate `Timer` with 25 MTOP timer items.
4. **Maintainer's feedback format**: L1 expects `{text,label}`/`{query,gold}`; L2 expects `{id,src,kind,user,answer}` + positional label; L9b `{user,answer}`. The three CLIs are mutually inconsistent and not documented in one place; any mismatch is an automatic crash.
5. **Calibration mismatch**: all covariances are from MASSIVE/CLINC prompts. L1's source-ablation (calibrate on one source, test on the other) shows .88-.90, so it should transfer; L2/L9b have no such ablation.
6. **More than 25 mistakes of mixed kinds / repeated feedback**: no entry supports a second feedback round (L1 deletes `patch.pt` and restarts from the original; "keeps learning" is one-shot).
7. **Runtime**: L2 needs 96 GB + 54 GB cache, L9b >= 40 GB; maintainers on a 24 GB card can only run L1.
