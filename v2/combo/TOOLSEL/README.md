# COMBO TRACK 2: TOOLSEL (tool selection as the label) + new-tool-as-new-label feedback
Dev data only. Locked rows (locked.jsonl, S2) were never read, scored or hashed (only LOCK.json counts/sha were used). No commit/push. Box: tenpct-g17 (g7e.4xlarge, RTX PRO 6000 96 GB), HF transformers, greedy.

## 1. Exam (done, dev part)
- `build_toolsel.py dev` -> `data/toolsel_{dev,calib,pool}.jsonl` (+ `eval_dev_items.jsonl` 1063 items, `calib_items.jsonl` 120, `MANIFEST_dev.json` with sha256s). dev = s1_dev + s3_dev (3397: xlam tool 1659 / none 829, s3 tool 746 / none 163); calib = s1_calib (2877); pool = s1_pool + s3_pool (14883).
- Label rule: nocall -> `none`; single with 1 gold call -> gold tool name (must be in menu, names unique, no tool called none, menu text <= 5000 chars); **multi dropped** (the "first" call of a multi item is not a well-defined single answer for a name-only router). Prompt text identical to research/C_tasks/build_tasks.py.
- `toolsel_scorer.py`: strict exact match (20 unit tests): output after removing <|im_end|>/<|endoftext|>/empty think block and .strip() must equal the label; empty/EOS-only, two names, quotes, backticks, trailing period, case change, JSON call = wrong.
- Locked set = deterministic function of locked.jsonl: `HASH_PLAN.json` + `LOCKED_BUILD_OK=1 python build_toolsel.py locked OUT` (refuses without the env var; asserts locked.jsonl sha == LOCK.json; prints only cell counts; exits non-zero if any cell < 330 or S2 < 500). Upper bound from LOCK counts: S1 tool 450, S1 none 400, S2 (BFCL) tool 500, S2 none 400 = 1750 items, no sampling, no back-fill from multi. NOT run. Risk: if BFCL tool names/length filters drop S2 tool below 500 the build fails loudly (S2>=500 total is still met by tool+none = 900).
- Base accuracy, real greedy generation + strict scorer, full dev exam (3397): Qwen3-4B 0.899, 8B 0.899, 14B 0.858. Per cell (4B/8B/14B): xlam tool .957/.972/.990, s3 tool .965/.946/.953, xlam none .788/.789/.598, s3 none .571/.503/.393. The `none` cells are the hard part. Always-`none` = 29% overall.
- **Honest difficulty note**: a 20-line lexical-overlap baseline (pick the menu entry with highest query/description token overlap, never `none`) scores 98.8% on xlam tool and 87.9% on s3 tool items; 31% of S1 tool and 26% of S3 tool menus have exactly ONE tool. So the tool cells are nearly "copy the only/best name"; the task's real content is the `none` decision.

## 2. Feedback as NEW LABEL (`toolsel_fb.py`, `analyze.py`, `table.md`, `results/*.json`, `results/PREREG_*.json`)
Design. Scenario = a PAIR of new tools (A,B) from s1_pool (6 pairs from 16 tools having >=30 near-duplicate-clusters of queries; xlam_pool families are disjoint from xlam_dev/calib by T1 construction). The new tool is NOT in the prompt menu (menu = original item menu with the gold tool removed, exactly how T1 builds nocall items), correct answer = the new tool's name. Base answers an old tool or `none` (base teach accuracy 0.00 in all 36 scenarios). Annotations <= 25 drawn from base-wrong annotation-pool queries; teach (29-93 queries/scenario, >= 25), dev, annotation pools are split by **query-cluster** (word-Jaccard >= 0.7 single-linkage clusters, exact duplicates removed) so no teach query is >= 0.7 similar to an annotation query; teach ids + sha256 written to `PREREG_*.json` before any edit. Strict subset (Jaccard < 0.5 to every annotation query) accuracy equals the full teach accuracy within 3 pts (8B). xLAM queries per tool are heavy paraphrases (before dedup 48-122 queries but only 30-77 clusters), which is why only 16 tools qualified and why this is "unseen paraphrase", not "unseen template".
Arms: N = natural name (e.g. `cell_density`, multi-token, first token often query-predictable); D = distinctive single-token first token (`Nova_<name>`, `Atlas_<name>`; both single Qwen tokens, 0 occurrences as first token of any T1 tool name, rest of the name still multi-token).
Neighbours: N1 = 400 base-verified-correct dev items (250 tool + 150 `none`, xlam_dev + s3_dev); N2 = 300 base-verified-correct same-family old-tool pool items with A,B stripped from menus. Controls per draw: empty (byte-identical, base), wrong-label (annotations labelled with a random existing tool from their own menu), 50/50 mixed (half carry the base's own wrong output), derangement (A<->B labels swapped). n in {3,5,8,12,25}, 30 draws each, 6 scenarios per (model, arm). CIs: cluster bootstrap (scenario, then draw). Gate G2 as feedback_v3: gain >= +15 pts (CI lo > 0), real minus each control >= +10 pts (lo > 0), N1 and N2 >= 98% (point), 0 bytes added (lm_head rows edited in place).
Evaluation is exact teacher forcing on cached hidden states (lm_head-only edits do not change hidden states); cross-checked by real HF generation + strict scorer on teach set and 200 N1 items for one config per scenario: agreement 0.90-1.0 on teach (36 scenarios, mean ~0.99), 1.0 on N1.
Methods: lmhead_lda (gray: generic mu/Sigma from unlabelled chat text + unlabelled calib prompts, alpha chosen on a labelled dev set from {0.05..4}, subject to dev-neighbours >= 0.98), lmhead_plain with FIXED alpha 0.03 (and 0.01) declared in advance (same constants as feedback_v3, not tuned on anything here), lmhead_cal / cal2 (per-token alpha self-calibrated to flip the annotated sites with margin 1, still uses generic mu/Sigma).

Heterogeneity: per tool pair teach accuracy ranges 0.0 to 0.93 (8B, lda n=25): the pair simulate_query_database / linear_regression_prediction is never taught by lda (dev-chosen alpha 0.05). The pooled number hides that.
Findings stated plainly:
1. In-menu headroom is nil: if the new tool is listed in the menu, base accuracy on the same queries is 0.94-1.0 (column V1 in table.md). A feedback story for TOOLSEL therefore only exists when the target name is NOT in the menu (label extension / the base picked an old tool or `none`).
2. Natural names are taught better than prefixed "distinctive first token" names (hypothesis in the brief was the opposite): the natural first token (`whole`, `find`, `calc`) is predicted from the query words, so boosting it is cheap; `Nova`/`Atlas` have to be created from nothing. Only cal at 14B passes for D.
3. Selective at 8B and 14B (N1/N2 >= 0.99, specificity: derangement control gives ~0, wrong-label gives 0); not selective at 4B for cal (leaks onto `none` items).
4. Nothing with a FIXED label-free alpha works (plain). Methods that pass use generic mu/Sigma (gray on rule 4 as in feedback_v3) and cal chooses alpha per token from the annotations' own margins (no dev tuning, but data-fitted).
5. n=25 fails the strict mixed gate for every method by saturation (see feedback_v3 section 1); n=3..12 pass for 8B/14B N-cal. Gains are partial (0.2-0.7 absolute, not ~1.0).
6. Not tested here: the real quantised codec (feedback_v3 section 6 already showed the lm_head per-row edit is rounded away at ~3 bpw with the stand-in codec), real-model sensitivity to menu order, S3-sourced new tools (S3 tools have 1-2 queries each, so no teach set), argument generation.

## 3. Compression (existing results; `compression_confirm_raw.txt`, D_scale/ct_analyze.py)
TOOLSEL retention vs bf16-correct items, 9.6% size, kind of calibration (items = C_tasks items.jsonl TOOLSEL part, 510-524 items):
- Qwen2.5-72B: plain allocation `t096` 0.931 (worst cell 0.894); `C72_gam1` (tool-call text calibration from s1_calib + layer-importance gamma=1) **0.971 (Wilson lo 0.953), cells: xlam none 1.000, xlam tool 0.973, s3 none 0.951, s3 tool 0.951** -> 98% overall gate NOT met (lo 0.953), per-cell >= 95% met by a hair.
- Qwen3-32B at 9.6%: t096 0.916; gam1 0.961; gam2 0.975 (cells s3 none .879, s3 tool .980); R3_kl 0.955; label+tool calibration mix (LCM_mix) 0.922 = no help; at 12%: 0.978; 15%: 0.990 (worst cell .981).
- So the calibration that helps is tool-call-text calibration (s1_calib) + importance gamma; calibrating on TOOLSEL label items does not. The weak cell is S3 `none`/`tool` (OOD ToolACE) and the 98% Wilson gate is not reached at 9.6% for any model tested.
- **Data caveat**: 141 of the 300 xlam-derived TOOLSEL query texts in C_tasks/items.jsonl (and 16 of 30 in calib.jsonl) are not in any non-locked split of the re-sliced T1 (s1_dev/calib/pool): they came from the OLD dev files and may overlap the new locked set. Retention numbers on them are valid as compression-quality measurements (compression never trained on them), but the TOOLSEL calibration file calib.jsonl should not be reused. The compression runs above calibrated on s1_calib tool-call text, which is clean.
- Eval inputs prepared for the final artifact: `data/eval_dev_items.jsonl` (1063 items, same schema as items.jsonl: id, task, role, src, kind, user, answer; cells s3 none 163 / s3 tool 300 / xlam none 300 / xlam tool 300), `data/calib_items.jsonl` (120, from s1_calib), full exam `data/toolsel_dev.jsonl`. Not re-run on compressed models (no compressed 72B/32B on this box; 96 GB cannot hold a 72B bf16 reference).

## 4. Rule 7 assessment (be honest)
Argument for: the output is the task's real production output of an agent tool router (MCP/agent frameworks do a selection step whose result is a function name), generated freely by the full lm_head, no letters, no constrained decoding, name vocabulary open (1837 distinct first tokens in the T1 menus), and `none` is a real decision. Argument against, and the risks I would not hide: (1) the menu is in the prompt and the answer is one of the listed strings, so a reviewer can call it multiple-choice with names instead of letters; for tool cells the model mostly copies a name from the prompt (lexical baseline 98.8% on xlam tool cells, single-tool menus 26-31%); (2) it drops arguments, i.e. the hard half of tool use, which is exactly what the maintainer's T1 exam scores; (3) the new-tool feedback only has headroom when the name is NOT in the menu, which is not how a real router is deployed (a deployed router lists its tools), so the feedback story is "teach an output string", the same shape as the taxonomy-extension test that the maintainer may or may not accept; (4) gain is partial and pair-dependent. Recommendation: TOOLSEL is a defensible auxiliary kind but not safe as the sole task; as a complete task it fails the compression gate (<98% Wilson at 9.6%) and the feedback gate only passes for natural names on 8B/14B with a gray (fitted generic-stats) method.
